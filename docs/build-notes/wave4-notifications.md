# Wave 4: integrations and notifications (w4ntf-)

## Summary
Integrations (spec 12.1) and notifications (12.2, 12.3) now run on real code from the screen to the wire. A connector registry lists the real connectors (GitHub, Slack, email by SMTP, signed webhook) and the ones that are not yet available (Teams and the rest), custom types are a signed webhook in and templated HTTP out, and every instance is created switched off. One hook on event append turns committed events into outbox rows and delivery-log rows in the same transaction. The worker delivers them (Slack bot token with chat.postMessage and chat.update, SMTP, signed webhooks, custom HTTP), keeps the log, and a dead delivery is itself a notification. `/hooks/slack` takes button clicks and `/gantry link` with signature, window and replay checks, and in-chat approval is a command like any other.

## Public interface
- **db** (`packages/db/src/events.ts`): `addEventObserver(fn)` and `onObserverError(fn)`. An observer runs in the event's transaction under a savepoint, so its failure never undoes the event. Migration `0021_notify_deliveries_chat_links.sql` adds delivery-log columns (project, event type, target, route, wo, message ref, card key, outbox id), `notification_routes.version`, `chat_link_requests` and `gate_votes.chat`.
- **api core export** (`@gantry/api/core`): `registerNotificationProducer({publicUrl})` (the API registers it in the notifications route plugin, the worker in its constructor), `slackPost`, `slackUpdate`, `slackAuthTest`, `notifyEventFor`.
- **Endpoints**: `GET/POST /integration-types`, `DELETE /integration-types/{id}`, `POST /integration-types/{type}/test` (the Add dialog's test of unsaved settings), `GET/POST /integrations`, `PATCH/DELETE /integrations/{id|channel}`, `POST /integrations/{id}/test`, `GET/POST/DELETE /chat-links`, `GET/POST /projects/{id}/routes`, `PATCH/DELETE .../routes/{rid}` (If-Match required), `POST .../routes/test`, `GET /deliveries` (cursor), `POST /deliveries/{id}/retry`, `GET/POST /card-templates`, `DELETE /card-templates/{id}`, `POST /card-templates/preview`, `POST /hooks/slack`, `POST /hooks/teams` (501: not yet available).
- **Code**: `services/api/src/areas/integrations/` (connectors, store, commands, ops, secrets, links, chat-policy, slack-hook) and `areas/notifications/` (events, cards, routing, emit, producer, commands, store, slack, http). Web: `views/integrations.tsx` + `integrations/`, `views/notifications.tsx` + `notifications/`.

## Behaviour worth knowing
- **Secrets**: all secret fields of an instance are sealed into one envelope (JSON by field key, AAD `integration:<id>`). Responses carry the mask of the first secret only. Rows, events and responses never hold a value (tests assert it).
- **Switches**: a new instance is off (`enable: true` on create is the explicit act). In-chat approval is off (`config.approve`), named per gate (`config.approveGates`), and never for G6, G3G3s, hotfixes, security holds or risk-tagged changes. The policy is checked before the decision point (so the reason is the real one) and again under the lock.
- **Producer**: maps ledger events to the notification catalogue (`areas/notifications/events.ts`), applies route conditions (class, priority, business hours in the org's tz), repo overrides (`repos.data.notifyOverrides`, also or instead) and card templates. Kill and restore ignore switches and conditions, their routes cannot be disabled, narrowed or removed, and with no route they go to every enabled connection's default target. A destination that cannot be resolved is a `failed` delivery with the reason; Retry resolves it again.
- **Cards**: a Slack gate card stores its message reference in the delivery row. When its gate instance is no longer open (decided, sent back, new head, killed) an `update` outbox row edits it in place and removes its buttons. Chat cards offer Approve and Open; reject needs a reason, so it stays in Gantry.
- **Chat identity**: the signed-in person asks for a one-time code (hash stored, 10 minutes), then sends `/gantry link <code>` from Slack. One chat user maps to one person; inactive people never resolve. Stored with the vote: channel, chat user, person, instance id, connection (`gate_votes.chat`, plus a `chat.approve` event).
- **Delivery failure**: a delivery that dead-letters appends `delivery.failed` (a notification event). A test send and a delivery-failure notice never produce another failure notice.
- **Web**: both screens ported with the legacy classes and ids; previews come from `POST /card-templates/preview`, which uses the same builders as the producer. Dropped on purpose: the simulated connection test and the "simulated" footnotes. Added: connection manifest and not-yet-available reasons, "Switch it on now", chat linking in the Slack drawer, a request body template in the custom builder, the retry/status vocabulary of the real log.

## Integration notes
1. `deploy/compose.yml`: the api gets `GANTRY_EGRESS_PROXY=http://gantry-edge:8444` for connection tests. The worker already has `HTTPS_PROXY`. `slack.com` is on the edge's system allow-list; a custom type's endpoint host is allowed because the edge reads it from the instance config.
2. `GANTRY_SLACK_API` overrides the Slack API base (tests and doubles). Slack's app needs interactivity and slash command URLs pointing at `/hooks/slack` and the signing secret entered on the connection.
3. `packages/domain`: `NOTIFY_EVENTS` gained `gate.escalated` and `delivery.failed`; `IntegrationType` and `Delivery` gained optional fields. Rebuild dist for domain, db and api before the worker typechecks.
4. New dependency: `nodemailer` (and its types) in `@gantry/api` for the SMTP connection test. The worker already had it.
5. `apps/web/src/api/ops.ts`: `updateIntegration`, `saveRoute` and `deleteRoute` take `Versioned`; new `testIntegrationDraft`, `requestChatLink`, `removeChatLink`; `sendTest` accepts a destination object; `removeCardTemplate` takes a project. `queries.ts`: `useRoutes` returns versions, `useChatLinks`, wider `useDeliveries` filter. `keys.ts`: `chatLinks`.
6. The stop path now also writes outbox and delivery rows through the observer. They are best-effort under a savepoint, so a stop still works when those tables are unreadable (the I7 test passes).

## Unverified
- Real Slack, real SMTP relay, real vendor webhooks: delivery and tests ran against local doubles (a Slack Web API double, the worker's SMTP double, a webhook receiver). Slack's real request shapes and signature were built from Slack's published v0 scheme, not captured from Slack.
- Slack interactivity from a real workspace, including `response_url` replies, the bot being in the channel, and `@person` targets (a user id is posted as the channel; names are not resolved).
- The edge allow-list end to end for the API's own connection tests and the worker's deliveries (the proxy client is tested against the worker's `FakeProxy`, not the real edge).
- The SMTP connection test goes straight to the host (SMTP does not pass an HTTP proxy), so it works for the internal relay and an allowed host only.
- Microsoft Teams: listed as not yet available; no delivery code path is exercised.
- Business-hours conditions use the org's tz label (`IST` maps to Asia/Kolkata, other values are read as IANA names).
- Multi-replica worker claims for the outbox were not exercised beyond the existing skip-locked tests.
