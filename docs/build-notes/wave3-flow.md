# Wave 3: flow engine, command side and reads (w3flow-)

## Summary
Work orders, gates, moves, the station-execution side, stop controls, the floor with replay, the record and the work-order parts of home are built in `gantry-api`. The api suite passes against real Postgres 17 (32 new tests in `test/flow-*.test.ts`): F1 (idempotent submit, also under a race), F2 (concurrent moves, one wins), F3 (superseded result and a stop's fencing), F5 (slot limit under concurrent dispatch, released on send-back and kill), F6 (double approve counts once, rule edited between votes), I4, stop precedence and refusals, a full walk across the route to done, epics, and a denied and a stale case for every command.

## Public interface
Routes (all state changes go through `command()` / `stopCommand()`; reads return the legacy shapes):
- `POST /api/v1/projects/{id}/work-orders` (idempotent; body `repo,title,description|body,priority,requestedCls|cls,...`; returns `id, wo, classification, route, gates, version`), `GET` list (`q,cls,where,repo,prio,source,state(open|done|...),sort,dir,cursor,limit` -> `{items,next,total}`), `GET /api/v1/work-orders/{id}` (the legacy WorkOrder plus `version, gateProgress, allowed{approve,moves,can}, stop, route`), `GET /api/v1/conversations?project=&awaitingMe=`.
- `POST /work-orders/{id}/messages` (`kind` answer | question | followup), `/reclassify {cls,reason}`, `/confirm-brief`, `/decline {reason}`, `/move {target,reason,dry_run}`, `/send-back {toStation,note}`, `/park {bay,reason}`, `/unpark`, `/reassign {agent}`, `/retry`, `PUT /record/summary {text}`.
- `POST /gate-instances/{woId}:{gateId}[:{n}]/approve|reject`. With `:n` a stale click (instance closed, reopened on a new head) is a 409.
- `GET /work-orders/{id}/record`, `record.md`, `record/export` (manifest with sha256 per part), `changes`.
- `GET /projects/{id}/floor[?at=ms]`: `{project, workOrders, flowVersion, slots{used,total,holders}, gates, queue, stop, stops, at, replay?}`.
- `POST /stops {scope,id,mode,reason,inFlight,confirmText}`, `DELETE /stops/{scope:target}` (resume a halt), `POST /stops/{scope:target}/restore {reason}` (`pending:true` for the first of two Factory Admins), `GET /stops/impact?scope=&id=`, `GET /stops`.

For the worker, from `@gantry/api/core` (all take the worker's own transaction and flush their events and jobs themselves):
- `applyStationResult(tx, attemptId, fencing, result, {now?})` -> `{applied:true, woId, station, next}` or `{applied:false, code:'superseded'|'stopped'|'unknown', reason}`. `result = {status: succeeded|failed|interrupted|needs_person, summary?, output?, error?, usage?, observed?{checks, files, headSha, tests}}`. `observed` (GitHub, edge) wins over the agent's `output`.
- `expireLeases(tx)` (F9: bounded retry, then "Needs a person" after 3), `recordMerged(tx, org, wo, {prNumber, mergeSha})`, `recordNewHead(tx, org, wo, headSha)`, `handleFlowTimer(tx, payload)` (escalation; paused by a halt; `lease_expiry` runs `expireLeases`).
- `reconcileStop(tx, stopRowId)` and `pendingStops(db)`; `flushFx`, `startAttempt`, `attemptIsCurrent`, `heartbeatAttempt`, `dispatchQueued`; the job contract `job()`, `parseJob()` in `core/jobs-contract.ts` (unchanged shape from the brief).

## Integration notes
1. Stop ids: the API id is `${scope}:${targetId}` (scope factory|project|repo|workorder); rows are `${scope}:${target}:${n}` (scope_type `wo` for work orders). DELETE resumes the active halt, restore lifts the active kill. Event types are the legacy ones (`halt`, `resume`, `kill`, `restore`, category `kill`, scope in `after`) so `stateAt` replays them. The budget system halt written by the internal runs code uses event type `stop.set` (not replayed on the floor).
2. Stop path and failure tolerance: `stopCommand` touches only `stops`, `restore_approvals` (factory restore) and `events`. The route then enqueues `stop.enforce` (dedupe `stop.enforce:{row}:v{version}`) in a separate step after the commit; if the jobs table is down the error is logged, the response says `enforcement: "pending"`, and the stop is already true (every command, submission and the edge read `stops` live; attempts below the stop's fencing are superseded). Migration 0017 adds `stops.enforced_at` and `reconciled_version`; the reaper should call `pendingStops(db)` each sweep and re-enqueue `stop.enforce` for what it returns (lost job or lifted stop never reconciled).
3. `stop.enforce` consumer (worker): call `reconcileStop(tx, payload.stopId)` first. It cancels attempts and revokes run tokens, releases slots and closes open gate instances on a kill, moves work orders to Killed on kill-cancel (remembering `data.killed.prev`), flags `heldByKill` on kill-hold, and on lift starts fresh attempts (halt resume, restore, per-work-order restore). The worker still has to do what the database cannot: terminate containers via the launcher, cancel queued `merge.request` jobs, ask the broker to fail the Gantry check / convert PRs to draft.
4. Attempts: `startAttempt` (inside enterStation) inserts the attempt and the `attempt.dispatch` job in the command's transaction; a second attempt for the same station supersedes the first (state `superseded`). Heartbeats extend `attempts.lease_until` (internal runs code); `expireLeases` handles lapses.
5. Gates: instance id `${wo}:${gate}:${n}`; the instance stores the rule version, policy version, flow version, head sha and `basis.required` (the N of M when it opened). A vote passes when `gateProgress` passes and `have >= max(required at open, required now)`: tightening applies at once, loosening never approves waiting work. The decision record (`gate_decisions`) holds the pinned versions, voters, trust level, tuple and commit. G0+G1 is the brief confirmation (one confirmation, writes `brief_versions`). Approving G5 with an open PR enqueues `merge.request` and waits; `recordMerged` advances. Without a PR it advances directly.
6. Slots: `slots` rows `${project}:${n}` go free<->held with an atomic upsert; every exit path (finish, send-back, park, decline, kill) releases and calls `dispatchQueued` (priority, then age in the bay).
7. `saveWo` skips an unchanged row, so the version bumps once per command. Every command locks the work order row (`lockWo`) and checks `If-Match` against the locked row; the pipeline's own pre-check is advisory.
8. Home: `areas/home/state.ts` got two small edits (killed work orders are loaded and carry `killed`/`heldByKill`); the compute code is unchanged and now sees real gate/conversation rows.
9. Web: `apps/web/src/api/ops.ts` already matches these bodies (`target`, `toStation`, `agent`, `inFlight`, `confirmText`, gate id `${wo}:${gate}`). `GET /conversations` and the work-order list return `{items,next,total}` (the web accepts both shapes).

## Unverified
- Real runs: `attempt.dispatch` is enqueued and applied results are exercised with test results; nothing launched a container. `observed` checks, commits and PR heads depend on the GitHub broker (no keys): the default for a mixed or automatic gate with no observed checks is the gate's own check list marked ok.
- Notification outbox rows (smtp, slack, teams, webhook) for gate waiting, questions, escalation and release are not produced here: the routing tables belong to the notifications area. Events carrying `gate.waiting`, `gate.escalated`, `wo.question` exist for it to key on.
- The edge's refusal within 10 s and the launcher teardown times of spec 4.4 are not measured (no stack was brought up).
- A restore of a kill-cancel re-opens the gate a work order was waiting at only when the instance was closed by that kill; a work order killed while running restarts its station.
- Replay (`?at=`) reads the last 14 days of work orders and 20000 events of a project.
