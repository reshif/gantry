# Wave 4: console

> **Superseded (2026-11-15): there is no factory-wide "Console actions" switch any more.** What the console may propose is decided per person by
> the `console.propose.*` rights in the role matrix (Govern > Access, Console group). Factory Admin holds all of them; nobody else holds any until a
> Factory Admin grants them to a role or team. `PUT /console/settings` always answers 409 with that pointer, and `actionsEnabled` in
> `GET /console/status` now means "this person holds at least one propose right". The model is told each turn which proposals this person may and
> may not make, so it can't claim actions are "switched off". Where this note mentions the switch below, read "the person's console rights".


## Summary
The Console (spec 8.9 Console row, 12.6) is real. `POST /api/v1/console/messages` streams an answer from a model called through the edge, with a fixed tool set that reads live data as the person (same visibility and permissions as the screens). Action tools never execute: they return proposals that the page draws as confirm cards, and confirming calls the ordinary endpoint under the person's own authority with `via: console`. Without a configured model the console says so plainly and answers nothing; the read tools and the slash commands still work. Action proposals are off in a new install. The screen is ported from `legacy/js/views/console.js` and `ask.js`, and an "Explain" affordance (legacy `G.explainDenial`) is added to the access simulator, the people cell detail and the security lock note. Real vendor calls are unverified (no key); the model loop is tested against a fake edge.

## Public interface
Endpoints (services/api/src/routes/console.ts, logic in areas/console/):
- `POST /api/v1/console/messages {text, threadId?, project?, via?}`: saves the question (command(), idempotent on `Idempotency-Key`, event `console.message` with length only, never the text), then streams SSE: `thread {threadId,messageId,created}`, `text {delta}`, `tool {name,ok}`, `proposal {messageId,proposal}`, `done {messageId,text,mode,model,cited,proposals,tools,usage,stopped}`, `unavailable {code,msg,messageId}` (no model), `error {code,msg,messageId}`. The answer is saved as an assistant message (or a `system` notice) in a second command() with event `console.answer`. A replayed Idempotency-Key answers with JSON `{replayed:true,...}` and makes no second model call. A client that goes away aborts the model call; what was said is kept, marked `stopped`.
- `GET /console/status` `{configured, vendor?, model?, code?, reason?, actionsEnabled, version, retentionDays, tools[]}`. `configured` asks the edge (`/service/v1/ready`): a route exists and the edge holds its key.
- `PUT /console/settings {actionsEnabled, reason?}`: the runtime switch for proposals (action `security.manage`, `If-Match` = settings version, a reason of 4+ characters to turn on, audited as `console.settings`, denial audited). Stored in `orgs.settings.console`; off in a new install.
- `GET /console/threads`, `GET /console/threads/{id}`, `DELETE /console/threads/{id}`, `PUT /console/threads/{id}/pinned`, `PUT /console/messages/{id}/proposals/{pid} {status,result}` (how a card ended, saved on its message). All own-data commands (action null); another person's thread reads as 404.
- `POST /console/tools/{name} {input}`: runs one tool directly (slash commands and tests). Read tools always; propose tools only while the switch is on (409 otherwise). Returns `{ok, tool, result, proposals, cited}`.
- `POST /console/explain {person?, action, project?, repo?, time?}`: "why not". Returns the policy engine's own trace and decision always, plus a model's plain-language `explanation` only when a model is configured (`mode: model|trace`, with a `note`). Explaining someone else needs the same right as the access simulator.

Tools (areas/console/tools.ts): read: `list_projects`, `list_work_orders`, `get_work_order`, `project_status`, `onboarding_state`, `who_can`, `explain_denial`, `waiting_on_me`, `evals`, `workload`, `trust`, `triggers`, `audit_search`, `events`. Propose: `propose_submit_work_order`, `propose_approve_gate`, `propose_halt`, `propose_resume`, `propose_kill`, `propose_restore`, `propose_park`, `propose_trust_change`, `propose_onboard_repo`. A proposal is `{id, kind, title, summary, steps, call:{method,path,body,idempotent}, perm:{action,project}, check:{allowed,reason,needs,rule}, needsReason, phrase, danger, entities}`. `check` is the decision point's answer for that person now (and a factory kill reads as refused for everything but a restore).

Edge (services/edge/src/service-gateway.ts, registered in gateway.ts): `POST /service/v1/messages` (Messages API body, `x-gantry-purpose: console|explain`, authenticated by the edge token; the model comes from routing, not the caller) and `GET /service/v1/ready`. The edge asks the API for the route (`POST /internal/v1/service-calls/authorize`) and reports usage (`POST /internal/v1/service-calls/usage`, areas/internal/service-calls.ts, edge-only via requireEdge). Metered into `usage_meter` with `station = console|explain`, no run and no project, priced at the version in force. The console's model is the routing default (or a factory station override named `console`), filtered like any run (connected vendor, enabled model, endpoint). No fallback alternates on this path.

Migration `0028_console_retention.sql`: `console_threads.retention_days` (default 90) and `expires_at` (moved forward `retention_days` after each message). Expired threads are invisible to reads and deleted by the next question (`purgeExpired`, also exported for a janitor).

## Behaviour that matters
- Visibility: read tools call the product's own GET endpoints in-process with the person's cookie and address, so a project, work order, audit row or trust cell they may not see never reaches the model. `who_can` lists people the person can already see (factory role or a role in a visible project).
- Untrusted text: titles, requests, reasons, commit and audit targets in tool results are wrapped `<untrusted>...</untrusted>` (a forged tag inside is defanged), and the system prompt says such text is data. The system prompt lists only projects the person sees.
- Without a model: the badge reads "No model", the mode line gives the reason (no default model, vendor not connected, no key stored, edge unreachable), a question is saved with a `system` notice and no answer, slash commands work.
- Audit: `console.message`, `console.answer` (mode, model, tools used, token counts, never text), `console.thread.deleted`, `console.settings`, and the ordinary events of confirmed actions (channel `console`, `on_behalf_of` the person).

## Screen (apps/web/src/views/console.tsx and console/*)
Same DOM classes and ids as legacy (`con-thread`, `con-input`, `con-form`, `con-send`, `con-stop`, `con-slash`, `con-foot-sug-*`, `con-ctx-project`, `con-pin-*`, `con-clear`, `con-cf-reason|confirm|mode|ok|no-*`, `con-ex-*`, `prop-*`), the same suggestions by role, slash menu with keyboard, entity chips, context panel (current project, what the person can do via `useCanMany`, pinned, "Your console actions" from the audit with channel console, clear), disabled-with-reason everywhere. Slash commands run the tools directly: `/projects /status /onboarding /onboard /new /why /who-can /approve /evals /triggers /halt /resume /kill /restore /changes /bottlenecks /summary /workload /trust /mine /help`; the ones that change state are propose tools and need the switch on.
New (the spec asks for it): the "Console actions" switch in the context panel (locked with the reason without `security.manage`, reason dialog to turn on); the mode badge says Model or No model; the answer streams; "Explain" (`ExplainDenial`, console/ExplainDenial.tsx) on a refused card, in the access simulator when the result is Denied, in the people cell detail, and in the security lock note.
Dropped, on purpose: the local intent matcher and every "local logic" answer (they were canned answers), simulation of triggers ("Simulate" on a trigger card; the trigger screen owns the dry run), the miniBelt in the status card, the legacy classifier preview on the new work order card (the work order is classified by the real intake when submitted), the "Claude runtime" availability probe and consent flow (`G.ask`).
Shared files touched (minimal): `apps/web/src/api/client.ts` (`streamCommand` takes an optional idempotency key), `services/api/src/routes/internal.ts` (one import, one register), `services/edge/src/gateway.ts` (one import, one call, one field in the returned object), plus one `ExplainDenial` import and element in `views/access/Simulator.tsx`, `views/people.tsx`, `views/security.tsx`.

## Unverified
- Real vendor calls: no key. The tool loop speaks the Anthropic Messages streaming format (text, `tool_use`, `input_json_delta`, `message_delta` stop reasons); an OpenAI-style custom vendor is not translated, the same limit as the run gateway.
- The model's behaviour (whether it calls the right tool, obeys the untrusted-data rule under an injection attempt) is not tested; only that the structure around it holds (marked text, the tool set, the visibility filter).
- Cost control: console usage is metered but there is no per-person or per-day cap on questions. The edge's vendor concurrency limiter applies.
- Retention: expired threads are deleted by the next question, and invisible before that; there is no scheduled janitor (`purgeExpired` is exported for the worker).
- Slash answers are client-side only and are lost on reload (the saved thread holds the model's conversation).
- Onboarding proposals call a strict endpoint that takes no `via`, so that action's channel is recorded as web.
- Multi-replica: the settings cache and readiness check are per request; no cross-replica behaviour was exercised.
