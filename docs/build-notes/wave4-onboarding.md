# Wave 4: repo onboarding (w4onb-)

## Summary
Repo onboarding (spec 8.6, 11.1, 11.3) is built from the connect wizard to the readiness re-check, against the real API, the real GitHub broker and the real worker, and the screen is ported from `legacy/js/views/onboarding.js`. Everything was exercised end to end with a fake GitHub (test double): connect, assessment from the repo's own files, onboarding PR, request changes, CI green, approve and merge, the live checks with the canary, Ready, loss of readiness (system halt with cause `readiness`), regaining it, an exception, repo settings and both guideline lists. Nothing ran against real GitHub (no App key): see Unverified.

## Design
- **Pure logic in `@gantry/domain/onboarding.ts`** (no IO, 27 tests): `RepoFacts` (what the broker reads), `assess()` (findings from facts: CI, test command, branch protection, CODEOWNERS, lint, secrets scan, AGENTS.md, toolchain pin, manifest and lockfile, MCP declared, Docker on the test path), `planPr()` (the files an onboarding PR adds, with real +/- counts), CODEOWNERS parser and matcher (last match wins, covers CI config, itself and `.gantry/`), `judgeProtections/judgeOwners/judgeCanary/judgeRunner/judgeGuidelines` (the "Verified means" list), `prChecksState()`, `readinessLost()` (only a definite failure loses readiness; an unanswered check never does).
- **Guidelines drive Ready.** Findings map to guideline items gl-1..gl-9 (`CHECK_GUIDELINE`); a required item that is not met blocks Ready, an advisory one is listed. `agents` and `docker` are always required (spec 16 D7). Project items are written into `AGENTS.md`.
- **The assessment adapter is `stub`** (deterministic, reads the repo's facts, no model). Its findings are facts, so no model is needed for them; the adapter name is stored on the run and shown. It does not run as a container run: runs belong to work orders (`runs.wo_id`, `attempts`), and onboarding has none. See Unverified.
- **State**: `repos.data.onboarding` is the current view (the legacy `repo.onboarding` object), changed only by `areas/onboarding/{commands,apply}.ts` in the same transaction as the event. History is in `onboarding_runs`, `onboarding_findings`, `onboarding_prs` (files with their added lines) and the new `onboarding_verifications`. `repos.onboarding_stage` mirrors the stage (it now allows `failed`).
- **Commands never wait for GitHub.** A command checks, records and enqueues a job; the worker reads GitHub through the broker and calls `apply*` (exported from `@gantry/api/core`), which re-locks the repo, ignores a job whose `runId` is no longer the repo's current run (or a repo marked ready by exception), changes state and enqueues what is next.

## Public interface
**API** (`routes/onboarding.ts`, all writes through `command()`):
- `GET /api/v1/projects/{id}/repos` (existing), `GET /api/v1/projects/{id}/repos/available` (`{available: [{repo, lang}] | null, unavailable?}`, from the broker; needs `repo.onboard`).
- `POST /api/v1/projects/{id}/repos {name: "org/name", team?, source?}` (action `repo.onboard`, `Idempotency-Key`; returns `{repo}` in the legacy shape with `version`). `PATCH /api/v1/repos/{id}/config` (`onboarding.manage`, `If-Match` required: team, mcp, notifyOverrides, triggers, source, tags, guidelines, config{defaultBranch, branchPrefix, merge, tagging, requiredChecks, protectedPaths}).
- `POST /api/v1/repos/{id}/onboarding/{assess|open-pr|verify}` (`onboarding.manage`), `/merge` (`onboarding.merge`), `/request-changes {text >= 5}` (`onboarding.manage`), `/exception {reason >= 10}` (`onboarding.exception`; lifts a readiness halt). `GET /api/v1/repos/{id}/onboarding/pr` (files with added lines). `If-Match` is optional on these (repo version).
- `GET /api/v1/guidelines`, `PUT /api/v1/guidelines {patch:{items,may,mayNot}, note>=3}` (`agent.edit`, `If-Match` = current version, required), `PUT /api/v1/projects/{id}/guidelines {patch:{items,notes}, note}` (`onboarding.guidelines`, `If-Match` required, 0 for none yet). Versions are immutable `guideline_versions` rows. `GET /projects` now carries `guidelines {items, notes, version, history}` from them.
- `POST /internal/v1/onboarding/fence {repo, purpose: write|merge|canary}` (github service token): a kill refuses all, a halt refuses only the merge (as the decision point does), a readiness halt refuses nothing, archived refuses all.
- Refusals: stopped scope is 409 with the stop's reason (the decision point's own wording), stale 409, validation 422, denied 403 (audited as `<action>.denied`).

**Broker** (`services/github/src/onboarding.ts`): `POST /v1/onboarding/inspect {repo, scan?}` (tree, key files, language, secrets scan reporting path/line/rule only, protections; 404 `not_installed`, 409 `empty_repo`), `/v1/onboarding/pr` (one branch + one PR, idempotent, `workflows` write only when a workflow file is added, optional comment), `/v1/onboarding/merge` (exact head, F4 re-read), `/v1/onboarding/canary` (canary branch, draft PR opened and closed, wait for a CI check, direct-push probe with an empty commit, always cleaned up), `GET /v1/installation/repos`. `readProtections` now reports `gantryCheckPinned`.

**Worker**: jobs `onboarding.assess|open_pr|merge|verify|sync` (queue `github`, in `jobs-contract.ts`). Recurring `onboarding.sync` per repo with a GitHub identity: every minute for open PRs and merged-not-verified, every `WORKER_READINESS_EVERY_MS` (default 6 h) for Ready repos, which enqueues a scheduled `onboarding.verify`. Config (all optional, env): `RUNNER_TOOLCHAINS` (`base=node,python;go=go`, default `base=node,python`), `WORKER_READINESS_EVERY_MS`, `WORKER_CANARY_EVERY_MS` (24 h), `WORKER_CANARY_WAIT_MS` (120 s), `GITHUB_GATE_CHECK_NAME`.

**Readiness**: a scheduled check that definitely fails twice in a row (`READINESS_STRIKES`), or a person's own verification that fails once, moves the repo to `person` and raises a repo-scope halt with `cause = 'readiness'`, `set_by = 'system'`, event `halt` plus `onboarding.readiness.lost` (outcome regression), enforced by the normal `stop.enforce`. Passing again (or an exception) lifts it. A broker or GitHub outage gives `unknown`, never a halt. A repo already halted by a person keeps their halt. A repo ready by exception and a repo with no `github_full_name` (demo data) are never re-checked. A scheduled check skips the canary except once a day, and the canary is not tried while the branch rules are missing (the push would prove nothing); the last result of a skipped check is carried forward with its date.

**Web** (`views/onboarding.tsx`, `views/onboarding/{kit,Pipeline,Drawer,Settings,Wizard,Agent}.tsx`): same DOM classes, ids, texts and controls as legacy; locks come from `useCan` with the repo in scope; `ops.saveGuidelines` takes an optional `Versioned`.

## Unverified
- Real GitHub or GitHub Enterprise Server: the permission names, `workflows` write on the App, ruleset and branch-protection field names, `integration_id` pinning, the rejection text of a direct push, check runs on a draft PR and the installation listing are written from the REST docs and tested only against the fake. The canary's "rejected" verdict needs GitHub's message to match `protect|rule|required|pull request|status check|review|restrict|not allowed|forbidden|must be made through`, else it is `unknown` (never a failure).
- The onboarding agent does not run as a model-driven container run; the assessment is the deterministic `stub` adapter. Request changes records the person's text as a PR comment and regenerates the files from the repo and guidelines; it does not interpret free text.
- Docker-needing repos are detected from compose files, test scripts and testcontainers only. Secrets are detected by pattern (AWS, GitHub, Slack, Stripe, Google, Anthropic keys, private keys, high-entropy assigned values), not GitHub's secret scanning; the scan stops at 600 files / 24 MB and says so.
- Integrations, agents, MCP, triggers and vendors endpoints are stubs in this build (404): the source picker offers the GitHub App only, MCP and trigger lists are empty, and the agent panel says it could not be read. They fill in when those areas land.
- Notification outbox rows for `onboarding.pr` (opened, merged, failed) are not produced; that belongs to the notifications engineer.
- GitHub team slugs are assumed to equal Gantry team ids in the generated CODEOWNERS (`@org/<team id>`).
- No multi-replica worker run; the dedupe keys make a second worker safe by construction.
