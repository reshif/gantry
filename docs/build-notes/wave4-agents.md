# Wave 4: agents, skills and instructions

## Summary
Agents, skills and the instruction layers are built end to end: the API (spec 8.7 Agents and Skills rows, 10.2, 13.2), the four-layer instruction composition pinned on every run, and the two screens ported from `legacy/js/views/agents.js` and `skills.js`. An agent has a working configuration people edit and save; a version is an immutable snapshot of the saved configuration; what runs is the version on the floor. Promotion is refused until the station eval suite passed for that exact version, and the refusal says what is needed and is audited. Run against a real API and Postgres in Playwright, the screens match the legacy pages (same DOM, ids, classes, texts); every control was exercised once (see Verified).

## Public interface
Endpoints (all under `/api/v1`, all state changes through `command()`):
- `GET /agents` (legacy `Agent` shape plus `rev`, `suiteName`, `threshold`, `running`, and per version `eligibility {ok,text,score,run,suite,threshold,needs,runs}`), `POST /agents` (idempotent create; starts paused at 0.1.0 with its own suite), `PATCH /agents/{id}` `{patch,note}` (`If-Match` = `rev`, required).
- `POST /agents/{id}/versions` `{label,note}` (candidate snapshot of the saved configuration; label `1.2.3` or `1.2.3-rc1`), `POST /agents/{id}/versions/{v}/promote` (`v` is the label or the number; 403 `EVAL-GATE` with `needs` until the suite passed), `POST /agents/{id}/rollback` `{version}` (no gate; restores that version's configuration as the working copy; a candidate that never ran is refused).
- `PUT|DELETE /agents/{id}/skills/{skill}` (append to the order, or detach), `PATCH` with `skills: [...]` to reorder.
- `GET /agents/{id}/effective?project=&repo=&version=` (`version` is a label, or `draft` for the saved working copy; default the floor version). Returns `{text, hash, layers[{key,name,version,hash,text,commit?}], skills[], words, tokens}`. Only projects the viewer can see.
- `GET /agents/suites` (the promotion-gate picker), `GET|PUT /instructions/base` (`PUT {text}`, `If-Match` = base version, required, 20 characters minimum).
- `GET|POST /skills`, `PATCH /skills/{id}` `{patch,note}` (`If-Match` = `rev`, required; every save is a new frozen version, minor bumped), `PUT /skills/{id}/projects` `{projects: "all" | ids}`.
- Backend exports from `@gantry/api/core`: `pinRunConfig(db, {orgId, agentId, agentVersion, projectId, repoId, commit})` and the types `RunPin`, `InstructionPin`.

Web: `views/agents.tsx` with `views/agents/{kit,Config,Instructions,SkillsMcp,Versions,Trust,Create}.tsx`; `views/skills.tsx`. `agentsSelect(id, tab?)` (views/agents/kit) and `skillsSelect(id, tab?)` (views/skills) let other screens open one. `ops.ts` signatures changed: `newAgentVersion(agentId, label, note?, v?)`, `promoteAgent/rollbackAgent(..., v?)`, `saveInstructions(text, v?)`, `setSkillProjects(id, projects | "all")`. `api/types.ts` gained `AgentEffective` and `AgentSuite`; `useAgentSuites()` in queries.

## Design decisions
- **Working configuration vs versions.** `agents.data` holds the working configuration (model, fallbacks, autonomy, tools, mcp, stations, projects, budget, guardrails, suite, instructions, overrides) and `agent_skills` its ordered skills. A version (`agent_versions`, frozen by the existing trigger) snapshots model, fallbacks, autonomy, tools, skills, mcp, guardrails, budget, instructions and overrides. Staffing (stations, projects), the suite and the name are operational and not versioned. Saving never touches a published version. "On the floor" is `agents.live_version`; a version is a candidate until promoted (`data.promoted` lists every version that was ever live).
- **Eval gate (spec 13.2).** Eligibility reads the evals area's tables: the agent's suite (`agents.data.suite` to `suites`, threshold in `suites.data.threshold`, 0.85 if absent) and the latest `completed` run of it for this version. A run names its version in `eval_runs.data.version` (the label) or points at a version tuple (`tuple_id`) whose agent version it is. No suite, no run, a failed run or a score below the threshold all refuse with `needs`. The refusal is a 403 with rule `EVAL-GATE`, audited as `agent.edit.denied`. Rollback skips the gate.
- **I6.** There is no route an agent can call: `/api/v1` refuses service principals and run tokens only reach `/internal`; API keys fail the decision point for `agent.edit` and `skill.edit` unless a role grants it, and a key's actions never include them. Tests: the edge token and a real API key against four of these endpoints.
- **Four-layer composition (spec 10.2)**, `areas/agents/compose.ts`: factory base (`instruction_versions` scope base), project overlay (scope project, else the project's overlay column), the agent layer (the pinned agent version's instructions, plus what the project override changes and the guardrails), the repository guidelines. Skills follow in order, filtered to projects where they are enabled. `pinRunConfig` runs in the worker's `pinTuple` at dispatch and records: the version tuple (its `instruction_hash` is now the hash of the whole composition, not the agent text alone, and `skill_versions` are the resolved skill versions), and on `runs.data` the `instructionPin` (base version, project version, agent version, the repo guidelines text as read, with its commit) and `composed` (hash, layers with versions and hashes, skills, tuple id). `/internal/v1/runs/{id}/spec` composes from that pin, so a later edit of a layer never changes what a dispatched run was told; a run with no pin reads the latest published layers. The per-project model override is applied when the tuple's model is pinned.
- **Skills** are versions too (`skill_versions`); `skills.live_version` is the latest. An agent version stores skill ids; the version of each is resolved (pinned version, else the live one) when a run is dispatched.
- Migration `0024_agents_skill_order_instructions.sql`: `agent_skills.position` (the order is meaningful), and `clock_timestamp()` defaults on `agents.created_at` and `skills.created_at` so rosters keep seed and creation order. `packages/db/src/seed.ts` now stores each seeded agent's full configuration, version snapshots, skills' `when`, `owner`, `resources` and the base instructions version (4).

## Ported screens
Agents: roster, header meta, detail with Configuration, Instructions (four layers with edit dialogs, effective preview that shows unsaved agent edits at once, repo commit), Skills and MCP, Per-project, Versions (candidate form, eval-gated promote with the reason in the disabled button, rollback dialog, run suite link), Trust (cells, proposals, demotions, ceilings through `@gantry/domain`), History (audit ledger for the agent), create flow (5 steps), pause and resume, draft kept across tabs and screens. Skills: library with search and filters, coverage, Definition (save as a new version with a note), Agents (attach toggles), Projects (all or per project), Versions (with learning proposals and audit history), New skill with optional attach.

Dropped on purpose: nothing from the legacy screens is simulation. "Run suite" navigates to Evals, which owns suite runs. The 7-day success sparkline and spend come from real attempts and usage metering, so they are empty on a fresh install.

## Unverified
- The repository guidelines layer is the repo's `guidelines` text as stored in Gantry (set at onboarding and editable in the Instructions tab), pinned with the seed commit the run was dispatched with. The file is not fetched from GitHub at that commit at dispatch time, so an edit made directly in the repo that Gantry has not synced is not seen. This needs the broker to read `AGENTS.md` at a commit; nothing was run against real GitHub.
- Model lists in the agent screens come from `GET /vendors` and `GET /routing`, which belong to the models area. Until those exist the model shows "(not available)" and fallback and primary pickers are empty. The screens were written and tested against the legacy shapes.
- Eval runs and suites are another area's. The gate reads `suites`, `eval_runs` (score, status, `data.version`, `tuple_id`) and `eval_cases` (`body.skill` or `body.skills`, for coverage). The seed has none, so on a fresh dev install every promotion is refused with "No suite" or "No run", which is correct. When the evals area writes runs it must put the version label in `data.version` or set `tuple_id`.
- Spec 13.2 asks for a smoke run on every skill or instruction change. The events `skill.edit`, `skill.create` and `agent.instructions` are emitted; no eval job kind exists yet to enqueue.
- Trust "one level lower for a probation period after a version change" (spec 13.3) is the trust area's; promotion and rollback emit `agent.promote` and `agent.rollback` for it to react to.
- Skill resources are file names only; there is no store for the files that ship with a skill.
- `trust` ceilings and trust cells in the Trust tab come from `GET /trust/cells`, which is not built yet; the tab shows its empty state until it is.
