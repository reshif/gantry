# Wave 4: learning and workload

## Summary
The learning loop (spec 8.7 Learning row, 13.4) and the workload figures (spec 8.9 Workload row, 13.5) are built end to end: API, a findings refresh job in the worker, and the two screens ported from `legacy/js/views/learning.js` and `workload.js`. Signals come from real records (gate rejections with reasons, send-backs, reverts and incidents, classification overrides, intake misses, eval regressions) and are grouped into findings. A person drafts a proposal from a finding; a second person accepts it, and accepting applies the change only through the ordinary command for that change, leaving that command's own audit entry beside the learning one, with a recorded way to undo it. Verifying is a measurement of a metric and window declared before the change. Proposals are switched off in a new install. Workload is computed on the server from the work order records with the domain's workload functions. Run against a real API and Postgres in Playwright, both screens match the legacy pages (same DOM, ids, classes and texts).

## Public interface
Learning, all under `/api/v1/learning`, all need `learning.apply` (a project scope where the change names one), all state changes through `command()`:
- `GET /findings` (legacy `LearningFinding` plus `rev`), `GET /proposals` (legacy `LearningProposal` plus `rev`, `metric`, `windowDays`, `baseline`, `appliedAt`, `appliedBy`, `rollback {summary, available}`, `verification`), `GET /signals?days=` (new, newest first; a regression has `ref` = its eval run and no work order), `GET /settings` (`{proposalsOn, otherDeciders}`). Reads hide whatever is about a project the viewer cannot see.
- `POST /findings/refresh`, `PUT /switch {on, reason}` (a reason is needed to turn on).
- `POST /proposals` (idempotent) `{finding, kind, title, expected, change, metric: {target}, windowDays}`; `POST /proposals/{id}/accept {note}`, `/decline {reason}`, `/verify`, `/rollback {reason}`.
- Status words: stored as `open` (proposed), `applied` (accepted and applied), `verified`, `rejected` (declined), `rolled_back`; the API returns the legacy words `proposed | accepted | verified | declined | rolled_back`. Home's "to review" count still reads `status = 'open'`.
Workload: `GET /api/v1/workload?scope=<project id|all>&days=<1..30>`: `{at, days, scope, minN, projects, factoryWide, ids, totals, rows, teams, byCls, byProject, bottlenecks, needsPerson, suggestions}`. Suggestions are computed on the server (ported from the legacy view) with a structured `action` the screen turns into a link. A project the viewer cannot see is a 404. Read only: delegates go through `PUT /people/{id}/away`.
Worker: job `learning.refresh` (system queue, every 6 hours, also exported as `refreshLearningFindings` from `@gantry/api/core`).
Web: `views/learning.tsx` + `views/learning/*`, `views/workload.tsx` + `views/workload/*`, `ui/SortTable.tsx` (legacy `G.dataTable`: sort, pages, row click). `learningFocus({finding|proposal|tab})` (exported from `views/learning`) lets other screens deep-link. `api/types.ts` gained the `Workload*` and `Learning*` shapes, `queries.ts` the `useLearningSignals`, `useLearningSettings` hooks (and `useWorkload(scope, days)` keeps the previous data while it refetches), `ops.ts` `rollbackLearning` and `setLearningSwitch`.

## Design decisions
- **Evidence always, proposals behind a switch (spec 15.3).** Findings and signals are recorded from the first work order and the refresh needs no switch. Drafting, accepting, declining, verifying and rolling back refuse (403, rule `LEARN-SWITCH`, needs "Turn on learning proposals", audited) while `orgs.settings.learning.proposals` is off, which it is in a new install. `PUT /learning/switch` turns it on or off (reason required to turn on). The screen shows a note and locks the controls with the reason.
- **Findings** (`areas/learning/findings.ts`): signals of the last 30 days grouped by (kind, agent, project); a group opens a finding when it repeats on at least 2 records; an open finding takes in new evidence (cap 20); an addressed one is left alone, so signals after it was addressed open a new finding once they repeat. One open finding per key (unique index). The refresh never drafts or applies anything; a person drafts (the legacy scripted "system" drafts are not reproduced).
- **Two people (spec 13.4).** The drafter cannot accept while another active person who may decide learning proposals for that scope exists (403, rule `LEARN-TWO-PERSON`, audited). With one eligible person the drafter may accept; the screen disables Accept with the reason while a second person exists. The drafter may still decline.
- **Applying** (`areas/learning/apply.ts`): the same command functions the endpoints run (`saveSkill`, `addEvalCase`, `saveProjectGuidelines`, `saveAgent`, `putApprovers`, `updateClassCmd`), after the decision point answers for that command's own action (`skill.edit`, `eval.run`, `onboarding.guidelines`, `agent.edit`, `approvers.edit`, `class.edit`) and its stopped-scope check. Both events are written in one transaction with the proposal's status, so a refusal anywhere applies nothing. A skill edit is refused as stale when the text changed since the draft (`before` is taken from the server at draft time, never from the client). The change shapes are strict per kind.
- **Never weaken.** There is no proposal kind for graders, trust criteria or eval rules, and the schemas are strict, so nothing rides along. A guardrail only gains a path; an approver rule only gains a condition that asks someone else to approve; a route may not skip intake, verify, review or close, nor a station a human or mixed gate follows; an eval suite only gains a case. Rolling back a guardrail or an approver condition loosens a control, so only a person can do it (it is a person's command with its own permission check).
- **Rollback path** is recorded on accept (`proposals.rollback`: the kind, a sentence on what it restores, and the values needed). Rolling back goes through the same ordinary command, is refused when something else changed the same thing since ("edited again"), reopens the finding, and ends the proposal as `rolled_back`. An eval case can be removed only while nothing has run it (its results stay in the record otherwise); that delete is the one place this code touches `eval_cases` outside the evals area, and only for a case the proposal itself added.
- **Verified (spec 13.4).** A draft must declare a metric (at most `target` signals of the finding's kind, project and agent) and a window in days (1 to 90). Accept stores a baseline (the same count over the window before). Verify refuses until the window after the change has ended, then counts the signals from the live records; above the target it is refused with the numbers. Nobody can assert it.
- **Workload** (`areas/workload/compute.ts`): `loadInsight` (flow state, work orders of the visible projects) feeds the domain's `workloadSummary`; the payload drops the heavy work order objects. The figures are derived from the work order records (gate votes, decisions, conversation answers), which are themselves built from the events, votes and decisions tables.
- **Bug found and fixed on the way:** `areas/workorders/model.ts` only set a gate's `waitingSince` while it was open, so a decided gate had no wait time and the response-time and wait-on-people figures were always empty. It is now set from the instance's `opened_at` for passed gates too (flow-reads, flow-wo and workload tests pass).
- Event categories: audit category `agents` (as the legacy), events `learning.draft | apply | decline | verify | rollback | refresh | switch`, denials `learning.apply.denied`; subject type `learning`.

## Ported screens
Learning: header meta, tabs (Proposals, Findings, Signals), status strip, proposal cards (kind, pipeline, change with word diff, expected effect, declared metric and baseline, owner, finding and evidence, rollback sentence, history line), accept dialog with note, decline and rollback with a reason, verify dialog, findings with refresh, the draft dialog (all six kinds, with metric and window fields), signals table with type filter, sort and paging. Workload: header meta, scope and window, snapshot with refresh, bus-factor note, suggestions (top five, show all, links to the fix), people, teams, where work waits and minutes tabs with sortable tables, "insufficient data" under 5 observations, the person drawer, and the delegate dialog.
Dropped on purpose: "Draft with Claude" (no model call from the screen; "Fill in from finding" writes a plain starting text from the finding, which is a template, not a result), the "In this demo the eval check is simulated" wording, and the legacy scripted "system" drafts. Suggestion links open Project config or Trust on the right project but cannot select the approvers tab or the cell (those screens keep that state to themselves); "Open in People" navigates to `#people/<id>` and People does not read the parameter yet.

- Worker `test/learning.test.ts` (1): the job regroups, writes one event, does nothing the second time, drafts nothing. `system.test.ts` scheduler count updated for the two recurring jobs the trust and learning engineers added (it was stale).
- Web `views/learning.test.tsx` (14) and `views/workload.test.tsx` (9) against mocked fetch: DOM ids and texts, disabled-with-reason (permission, switch off, drafter), request shapes (If-Match not needed; Idempotency-Key on the draft), refusals shown inline, sort kept across tabs, scope and window passed to the server.
- Live: real API and Postgres (dev seed plus three finished and two waiting work orders, send-backs and eval runs), Vite, Playwright against `legacy/index.html` for the same person. Screenshots `/tmp/claude-0/w4ins-legacy-{learning,workload,...}.png` and `/tmp/claude-0/w4ins-react-*.png`. Each control exercised once: the switch, draft (validation, fill, guardrail and skill kinds), the drafter's locked Accept with its reason, a second person's accept with a note, verify locked until the window, rollback, decline, the three findings and signals tabs, refresh; workload scope, window, refresh, sort, the four tabs, the person drawer, the delegate dialog (set), the suggestion and row links.

## Unverified
- Rejections with reasons were exercised through the unit data (the domain function reads `gates[k].rejections`, which the work order model fills from rejected gate decisions); the live run's evidence was send-backs, intake misses and eval regressions.
- Classification overrides and revert/incident outcomes feed signals through the same domain function; covered by its domain tests, not re-run end to end here.
- "Verified" can be checked only after the window has really run; the tests move `applied_at` back to simulate time passing.
- Nothing here needs GitHub, vendor or Slack keys.
