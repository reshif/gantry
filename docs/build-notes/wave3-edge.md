# Wave 3: edge

## Summary
Built the gantry-github broker (:9200) and its API side: /hooks/github, the fence-check and events endpoints, and a store that copies GitHub facts into the Code tables. Everything passes against a fake GitHub HTTP API and a real Postgres, and the seed/publish workspace path is tested end to end with git and tar. Real GitHub is unverified because there is no App key. The broker mints one-repository, least-permission installation tokens per operation. It seeds workspaces and publishes through the git data API (blobs, trees, commits, refs), so commits are App-authored and GitHub marks them verified. Other operations are gate check, PR state, convert to draft, merge at an expected sha, protections, deliveries and a poll loop. Publish refuses a superseded attempt before any write and re-checks the fence before moving the branch. Typecheck is clean for @gantry/github and @gantry/api. 43 broker tests and 15 new API tests pass, plus 62 existing API tests (core, command, internal-runs). The 2 DockerWorkspaceStore tests passed against real Docker with GANTRY_GITHUB_DOCKER_TEST=1; they are skipped by default.

## Public interface
BROKER (http://gantry-github:9200, header `Authorization: Bearer <github_token>`; GET /healthz is open). Errors are `{ok:false, msg, code, ...}`: 401 no token, 409 fenced, 422 invalid, 502 GitHub or Docker, 503 API unavailable.
- POST /v1/workspaces/seed `{repo:'owner/name', commit:<40-hex>, volume:'ws-<id>'}`. Strict body. Shallow-fetches the commit in broker scratch space and streams the tree, with `.git` and its `shallow` file, into the volume as uid/gid 10001. Returns 200 `{ok, repo, commit, volume}`.
- POST /v1/publish `{attemptId, fencing, repo, volume, branch:'gantry/<woId>', base?, baseBranch?, title?, body?, draft?}`. Fence-checks with the API, copies git objects from a read-only mount, re-creates the commits through the git data API, updates `refs/heads/<branch>`, opens or updates the PR, then posts commits, per-file stats and patches to the API.
  - Returns `{ok, branch, headSha, noop, alreadyPublished, commits:[{localSha, sha}], pullRequest:{number, url, created}|null}`.
  - `base` is optional and defaults to the seed's shallow boundary commit.
  - Refusals: 409 `fenced` (superseded or stopped), 409 `branch_moved`, 422 `non_linear`, 422 `bad_branch`, 502 `record_not_stored` (retry is idempotent), 503 `api_unavailable`.
- POST /v1/checks/gate `{woId, repo, headSha, state:'passing'|'failing'|'pending', summary?, detailsUrl?}`. Check name is "Gantry gates" (GITHUB_GATE_CHECK_NAME). `failing` and `pending` stay allowed under a stop; `passing` is refused.
- GET /v1/pull-state?repo=&number= returns `{pullRequest, checks[], reviews[], approvals[] (approvals of the current head only), status, mergeable, mergeableState}`.
- POST /v1/pulls/draft `{woId, repo, number}` uses GraphQL convertPullRequestToDraft. POST /v1/pulls/merge `{woId, repo, number, headSha:<40-hex>, method?:'squash'|'merge'|'rebase', commitTitle?}` sends `sha` to GitHub. It re-reads the PR first, so a retry merges at most once. 409 codes: `head_moved`, `not_mergeable`, `not_open`. On success it posts the merged PR fact to the API.
- GET /v1/protections?repo= returns branch protection, rulesets, installation permissions, server version, `appOnBypassList` and `requiresGantryCheck`.
- GET /v1/deliveries and POST /v1/deliveries/reconcile (redelivers failed webhook deliveries once). POST /v1/reconcile `{repo, branchPrefix?}` is the `github.reconcile` job target. An in-process poller runs every GITHUB_POLL_INTERVAL_MS (default 30000; 0 disables) over the repos from the API.
- Installation permissions per operation: seed (contents r, metadata r); publish and merge (contents w, pull_requests w, metadata r); pull_request (pull_requests w, contents r, metadata r); gate_check (checks w, pull_requests r, metadata r); draft (pull_requests w, metadata r); read_state (pull_requests r, checks r, statuses r, actions r, issues r, contents r, metadata r); protections (administration r, contents r, pull_requests r, metadata r).
- The App must hold exactly the spec 11.1 set: Metadata r, Contents w, Pull requests w, Issues w, Checks w, Actions r, Commit statuses r, Administration r. Workflows write is added only if the onboarding PR adds workflow files. Issues write is never requested by the broker itself. Administration write, Secrets and org admin are never requested.

API (all /internal/v1 calls require the github service token; non-github services get 403):
- POST /internal/v1/attempts/{id}/fence-check `{fencing, purpose:'publish', repo?}` returns 200 `{ok, allow:true, woId, attemptId, projectId, repoId, repo, branch, reason}` or `{allow:false, code:'unknown'|'superseded'|'stopped'|'repo_mismatch'|'wo_closed', reason}`. Both outcomes write a `github.fence.passed` or `github.fence.denied` audit event. A stale fencing number or an attempt not in running/succeeded is `superseded`.
- POST /internal/v1/work-orders/{id}/fence-check `{purpose:'pr'|'check_pass'|'check_pending'|'merge'|'check_fail'|'draft', repo?}`. This is an addition beyond the spec. `check_fail` and `draft` are allowed under a stop; the others are refused.
- POST /internal/v1/github/events takes `{source:'poll'|'hook'|'publish', repo, pullRequests[], checks[], reviews[], issues[], publish?{attemptId, woId, branch, prNumber, commits[...]}}` (schema `GithubFacts`).
  - It upserts pull_requests, commits, changed_files, patches, checks, reviews and labelled issues.
  - A head commit Gantry did not publish emits a `github.drift` event and calls `recordNewHead`. A merge nobody asked for or a close without merge emits `github.drift`. A merge that closes a requested one calls `recordMerged`.
  - Returns `{counts, merged}`. An unknown repo returns 404.
- GET /internal/v1/github/repos returns `{repos:[{id, repo, installationId, projectId, defaultBranch, branchPrefix}]}` for repos with a GitHub identity.
- POST /hooks/github verifies X-Hub-Signature-256 over the raw body. The secret comes from `integration_instances` where type_id='github' and secret_enc is set, decrypted with the data key. Replays by X-GitHub-Delivery are acknowledged as duplicates without reprocessing. It stores the payload and an `inbound_deliveries` row and enqueues a `github.event` job, all in one transaction. It returns 202 `{ok, delivery, duplicate}`, 401 for a bad signature (audited as `github.hook.denied`), 503 if no secret is configured.
- Exports from `@gantry/api/core`: `processGithubDelivery(tx, orgId, deliveryId)` (for the worker's `github.event` job), `applyFacts`, `findRepo`, `fenceAttempt`, `fenceWorkOrder`, `GithubFacts`, `verifyGithubSignature`.

Migration 0016_github_blobs_deliveries.sql adds `github_blobs` (patches and raw webhook payloads, content-addressed by sha256), `commits.local_sha`, `commits.parent_shas` and `repos.github_full_name`.

## Unverified
- Real GitHub or GitHub Enterprise Server: no App key, so nothing ran against a real server. Token scoping, git-data publishing, check runs, GraphQL draft, rulesets and the delivery endpoints are tested only against my own fake. The exact GitHub permission names and which App permissions the target edition requires are still the spec 16 open item.
- The Dockerfile's `apk add git` step could not run here (no Alpine mirror), so the image was built with INSTALL_GIT=false. Seed and publish use the host git binary in tests only.
- The Docker socket is not mounted into gantry-github in deploy/compose.yml. The default `docker compose up` does not give the broker Docker access, so seed and publish fail with 502 until the compose follow-up is applied.
- Webhook secret lookup assumes the integrations engineer seals it with the data key under AAD `integration:<id>` (or no AAD) as plain text or `{webhookSecret}`; I tried both AAD forms but there is no integrations code yet to confirm.
- The `github.event` job consumer is not wired. I export `processGithubDelivery` from @gantry/api/core, but the worker must call it. The broker-side `github.reconcile` and the `merge.request`, `stop.enforce`, `publish` and `attempt.dispatch` handlers are also the worker's to build; the broker endpoints they call exist.
- Patches and raw webhook payloads live in Postgres (`github_blobs`), not MinIO, because the API has no S3 client yet. The hash keys match the MinIO convention, so moving them later is mechanical.
- Rate limiting is a per-installation token bucket (default 40 writes/min, burst 10) tested with a fake clock; it was never exercised against GitHub's real secondary limits.
- The spike for API-created versus `git push` commits (spec 11.4) was not run. API-created commits are implemented and unsigned push is not. Squash-merged history, merge commits in the workspace (refused as non_linear) and repos requiring signed commits were not exercised for real.
- Large repositories, clone depth beyond 1, submodules and LFS were not exercised; blobs over 50 MB are refused.
- The multi-replica NOTIFY of the SSE keys from the events endpoint was not checked beyond calling publishChange.
